## 3. Slack 最小权限：从漂移到达成

allowlist：

```text
app_mentions:read
chat:write
channels:history   # 公共频道
groups:history     # 私有频道
```

变更前，实际 bot token 有 12 个 scopes，额外包含 `assistant:write`、`channels:read`、`im:*`、`reactions:*`、`users:read`。远端 manifest 当时有 6 个 bot scopes、2 个 optional scopes、20 个 user scopes，以及依赖 `channels:read`/`im:history` 的未使用 user/channel events 和 Agent View。`scripts/check-slack-scopes.sh` 退出 1。

Slack CLI 已登录（A），`apps.status`/`manifest info` 可读。先同步一个只改 scopes 的 manifest 时，`apps.developerInstall` 返回 `restricted_scopes`：B 添加的 `admin.apps:read/write` 位于 **user scopes**，不是 bot 权限，且免费 workspace 不接受。经确认移除全部 user scopes；Bots 不使用 user token，未来需要 Admin API 应使用独立的 Enterprise Grid app/user token。

最终 manifest 变更（远端 before SHA-256 `bc432d0a…`，final `10a2bdb2…`）：

- bot scopes：`app_mentions:read`、`channels:history`、`chat:write`、`groups:history`；
- 移除 `bot_optional`、`user_events`、`channel_*`/`message.im` bot events；
- 移除 Bots 未实现的 Agent View；
- 移除全部 user scopes。

随后 uninstall/install 重新授权。旧 bot token 返回 `invalid_auth`；通过 CLI 的 `apps.developerInstall` 取得新 bot/app-level token，直接写回本地 `.env.slack.local`（0600，未打印），Socket Mode 重连成功，`/readyz` 200。`scripts/check-slack-scopes.sh` 退出 0。

## 4. Bots schema 备份/恢复演练

第一次尝试暴露两个真实运行错误：

1. 宿主机 `pg_dump` 17 对 PG16 服务器生成的 dump 在 restore 时包含 `SET transaction_timeout = 0;`，PG16 拒绝；脚本现在先比较客户端/服务器主版本，不匹配直接退出 2。
2. `pg_restore --schema=bots` 会过滤掉 dump 中的 `CREATE SCHEMA bots`，导致后续对象全部失败；Bots-only dump 恢复改为不传 `--schema`，并先检查目标库名称前缀 `bots_restore_` 且没有 `bots` schema。

使用容器内 PG16 工具完成实际演练：

| 步骤 | 结果 |
|---|---|
| dump | `docker exec ... pg_dump --schema=bots --format=custom`；SHA-256 `f944e3b07951700edfce5b6aaf2b9b5670982e4bc17b36501dd4e1f10169a390` |
| 目标库 | `bots_restore_drill_20261020102645`，专用测试库 |
| restore | `pg_restore --no-owner --no-privileges` 成功；没有 `--schema` 过滤 |
| 源/目标 `bots.bots` | 17 / 17 |
| 源/目标 `audit_events` | 273 / 273 |
| 清理 | 演练库已 `DROP DATABASE ... WITH (FORCE)`；未触碰源库 |

脚本 `scripts/backup-bots.sh`、`scripts/restore-bots-drill.sh` 已加入 `make check` 的 `sh -n`。本轮只覆盖 Bots 自有 schema；Chronotope run/timer/Restate 的协调备份和 RTO 仍未演练，不能声称全栈可恢复。

Chronotope 仓库已有 `test/dr/pitr.sh`（D1 PG PITR）、`test/dr/restate-backup.sh`（D3 Restate 卷恢复）、`test/dr/rustfs-restore.sh`（D2）。Bots schema 与 Chronotope 同库，D1 可覆盖；D3 会清空/重启 Restate，必须维护窗口。本轮没有执行这些破坏性全栈演练，联合 RTO/RPO 仍为阻塞项。

## 5. unknown/rejected 运行手册

`docs/部署与试用.md` 增加：暂停 Bot、到原 thread 人工核对、保留 delivery/task/audit ID、禁止直接改库或盲重发、每日检查。

`e6a078c` 增加 `POST /api/tenants/{tenant}/bots/{bot}/deliveries/{id}/resolve`：只接受 `unknown`；confirmed 必须带真实 provider message ID，rejected 必须带理由；行锁后更新 delivery 与匹配 task（completed/canceled），写 `delivery_resolved` 审计，绝不调用 provider 或重试。PG 回归覆盖 confirmed/rejected、重复解析冲突、跨 Bot 隔离和非法输入；HTTP 回归覆盖认证、body/state 校验。unknown 仍占用任务额度，但管理员现在有受审计的闭环动作。

## 7. 边界

- readiness 成功只表示进程/租约/Step/Socket 依赖就绪，不表示某个业务请求已送达或 Slack 安装已验收。
- `/readyz` 只暴露 ready/not_ready；这不是 metrics、告警或完整可观测性。
- 容器镜像构建成功不等于容器化 Chronotope 联调通过；systemd 模板也未在目标主机执行。
- 备份演练证明 Bots schema 的 dump/restore 路径；不代表 Restate/PG 全栈或 RPO 达标。
- Slack bot scopes 已在 allowlist 内并有真实 smoke；App Home/ngrok 设置仍保留但不再授予额外 bot scopes，后续可清理。
