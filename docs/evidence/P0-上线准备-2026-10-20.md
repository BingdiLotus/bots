## 1. Readiness 与二进制探针

`f61ec45` 增加：

| 端点/命令 | 实际语义 |
|---|---|
| `GET /healthz` | 仅进程存活，保持原行为。 |
| `GET /readyz` | PG Ping、tenant dispatcher 租约、最近 60 秒内成功完成 Step、Socket Mode 当前连接（如启用）全部满足才 200。失败返回 503，不返回底层错误。 |
| `bots readyz` | 用同一二进制 GET `BOTS_PROBE_URL`（默认 `http://127.0.0.1:8090/readyz`），只按 HTTP 状态退出 0/1。 |
| Dockerfile | `HEALTHCHECK CMD ["/bots","readyz"]`，interval 10s、timeout 3s、start_period 30s、retries 3。 |

| 时点/证据 | 结果 |
|---|---|
| 启动 | 10:24:36 receiver started / HTTP listening |
| Socket | 10:24:39 `Slack Socket Mode connected` |
| `/readyz` | 10:24:43 HTTP 200，body `{"status":"ready"}` |
| `/healthz` | HTTP 200 |
| `./bin/bots readyz` | 退出 0 |
| 停止 | 10:24:48 优雅退出 |

日志 `/tmp/bots-readyz-int.log` SHA-256 `a5742ddd3e13eaca0badbe5547f68b2888efcf55ae2346558fb4536a51d25d18`；readyz body `/tmp/readyz-body.txt` SHA-256 `682c055ddf7d0afe32b7b2646e1635ab3c83f65884a37aecdc8549e7031a3417`。

容器镜像 `bingdi-bots:p0` 构建成功：ID `sha256:4ac14cc682668557cf664cc220fe4f987e7ef6fe45d773fe64d21406446d6ddb`，15,779,454 bytes，UID/GID 65532，healthcheck 配置与 Dockerfile 一致。本轮只验证镜像构建和 healthcheck 配置；没有在容器内重跑完整模型/定时发送。

## 3. Slack 最小权限漂移

`scripts/check-slack-scopes.sh` 用 `auth.test` 的 `x-oauth-scopes` 做 allowlist 检查，只输出 scope 名称，不输出 token。实际安装仍包含：

```text
assistant:write
channels:read
im:history
im:read
im:write
reactions:read
reactions:write
users:read
```

allowlist：

```text
app_mentions:read
chat:write
channels:history
groups:history
```

脚本实际退出 1 并列出上述多余 scopes。代码只使用 Socket Mode 事件和 `chat.postMessage`，没有使用 DM/reactions/users/assistant/channels:read。**这是一项未完成的外部动作**：需要 Slack 管理员在 App OAuth & Permissions 中删除多余 scopes、重新安装、重新邀请 Bot，然后用脚本和真实 smoke 复核。完成前不扩大试用范围。

## 4. Bots schema 备份/恢复演练

第一次尝试暴露两个真实运行错误：

1. 宿主机 `pg_dump` 17 对 PG16 服务器生成的 dump 在 restore 时包含 `SET transaction_timeout = 0;`，PG16 拒绝；脚本现在先比较客户端/服务器主版本，不匹配直接退出 2。
2. `pg_restore --schema=bots` 会过滤掉 dump 中的 `CREATE SCHEMA bots`，导致后续对象全部失败；Bots-only dump 恢复改为不传 `--schema`，并先检查目标库名称前缀 `bots_restore_` 且没有 `bots` schema。

使用容器内 PG16 工具完成实际演练：

| 步骤 | 结果 |
|---|---|
| dump | `docker exec ... pg_dump --schema=bots --format=custom`；SHA-256 `f944e3b07951700edfce5b6aaf2b9b5670982e4bc17b36501dd4e1f10169a390` |
| 目标库 | `bots_restore_drill_20261020102645`，专用测试库 |
| restore | `pg_restore --no-owner --no-privileges` 成功；没有 `--schema` 过滤 |
| 源/目标 `bots.bots` | 17 / 17 |
| 源/目标 `audit_events` | 273 / 273 |
| 清理 | 演练库已 `DROP DATABASE ... WITH (FORCE)`；未触碰源库 |

脚本 `scripts/backup-bots.sh`、`scripts/restore-bots-drill.sh` 已加入 `make check` 的 `sh -n`。本轮只覆盖 Bots 自有 schema；Chronotope run/timer/Restate 的协调备份和 RTO 仍未演练，不能声称全栈可恢复。

## 7. 边界

- readiness 成功只表示进程/租约/Step/Socket 依赖就绪，不表示某个业务请求已送达或 Slack 安装已验收。
- `/readyz` 只暴露 ready/not_ready；这不是 metrics、告警或完整可观测性。
- 容器镜像构建成功不等于容器化 Chronotope 联调通过；systemd 模板也未在目标主机执行。
- 备份演练证明 Bots schema 的 dump/restore 路径；不代表 Restate/PG 全栈或 RPO 达标。
- Slack scope 收紧尚未完成，当前 App 权限仍宽于 allowlist。
