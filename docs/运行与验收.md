# Bots MVP 运行与验收

Bots 是一个 Go 进程，复用 Chronotope 的 PostgreSQL 服务，在独立 `bots` schema 保存原生对象。Chronotope API/worker 必须使用 `API_AUTH_MODE=on`；Bots 持有自己的 tenant key，不使用 bootstrap admin key 执行日常调用。没有第二个 scheduler、broker 或模型历史副本。

## 1. 最小本地配置

1. 复制 `configs/bot.example.yaml` 为 `configs/bot.yaml`，填入组织、Bot、测试频道和安装身份。文件仅保存环境变量名，不保存 token。模型名称须在 Chronotope 的 LiteLLM 路由中存在。
2. 按 `.env.example` 配置环境并导出。服务不自动加载 `.env`。`BOTS_CHRONOTOPE_TOKEN` 是该 tenant 的运行时 key；`BOTS_ADMIN_TOKEN` 是管理员 API key；`APPLICATION_SERVICE_TOKEN` 是 Chronotope 调用 Bots 工具及 timer 的服务 key，三者分别配置。
3. 启动前在 Chronotope 配置固定 bridge 和 timer target；API 与 worker 使用完全相同的配置。计时回调的 `scope_id` 由 Bots 的频道知识范围确定，与 thread 无关。

```json
APPLICATION_BRIDGES_JSON=[{"ref":"bots-native","tenant_id":"bots-dev","url":"http://host.docker.internal:8090/internal/tools","token_env":"APPLICATION_SERVICE_TOKEN"}]
APPLICATION_TIMER_TARGETS_JSON=[{"ref":"bots-timers","tenant_id":"bots-dev","subject_ref":"team-assistant","scope_id":"替换为计算结果","callback_url":"http://host.docker.internal:8090/internal/timer-fires","token_env":"APPLICATION_SERVICE_TOKEN"}]
```

上述是环境变量的值，不是 shell 赋值命令。`host.docker.internal` 用于容器访问宿主机；Bots 需监听 `0.0.0.0:8090`。其它部署使用实际可达的固定内网地址。

知识 scope 的计算与 `domain.KnowledgeScope` 相同；下例参数必须与 seed 完全一致：

```sh
python3 -c 'import hashlib,json; parts=["bots-dev","team-assistant","slack-dev","C_REPLACE"]; print("scope_"+hashlib.sha256(json.dumps(parts,separators=(",",":")).encode()).hexdigest()[:32])'
GOTOOLCHAIN=go1.26.0 make run
```

首次导入后 PostgreSQL 为配置权威，重启时 YAML 不覆盖管理修改。人格、SOP、模型、时区和限额可按 revision 在线修改；账号身份、频道、凭据引用及 bridge/timer 绑定固定首导入。更换这些绑定在本期使用新 Bot 或明确的开发重建，避免在途发送换账号。凭据值可在同一环境引用下轮换。

一个 tenant 仅运行一个 Bots dispatcher。启动持有 PostgreSQL session advisory lock；第二进程拒绝启动，连接丢失时 dispatcher 停止。这里没有多副本 HA 保证。

## 2. Slack 免费自建 App

普通自建 Bot 不依赖 Slack 内置 AI 订阅；免费工作区需有一个可用的 App 安装名额。官方依据及其它免费渠道见[免费测试渠道](research/免费测试渠道.md)。

1. 在 [Slack Apps](https://api.slack.com/apps) 创建工作区内部 App，启用 Bot user。
2. Bot token scopes 使用 `app_mentions:read`、`chat:write`；公共频道线程消息使用 `channels:history`，私有频道需要 `groups:history`。只启用实际测试频道所需权限，不开放 DM 或全工作区读取。
3. 安装到工作区，将 Bot 邀请到指定测试频道。在本地配置 Bot token 和 signing secret；`auth.test` 可只读确认 `team_id/user_id`。频道 ID 可从频道详情复制。
4. Events API 的 Request URL 指向公网 HTTPS 的 `/channels/slack/{tenant}/{bot}/events`。开发可以使用 HTTPS 隧道；内部工具/timer/管理员 API 不需要对公网开放。订阅 `app_mention`，以及所用频道类型的 `message.channels` / `message.groups`。
5. 首条消息显式 @Bot；已接纳的 thread 后续成员回复继续进入同一 session。其它 thread 的普通消息、自身/其它 Bot 消息和 DM 忽略。编辑/删除事件直接处理来源失效，不唤起模型。

真实 smoke 前指定测试频道和测试内容。预期操作是成员发起“记住测试事实，并在一分钟后提醒”，Bot 在该 thread 回复一次确认、到点回复一次提醒，再由成员在新 thread 查询记忆。真实外发需由测试环境所有者授权；本地 sink 验证不替代这一门槛。

## 3. 管理 API

管理页位于 `/admin`，直接使用以下 API，无单独前端服务。输入管理员凭据后可查看配置、知识、任务、回执和审计，修改人格/SOP 与执行限额，启停 Bot/账号或停用知识。账号和接入绑定只读。凭据仅保留在页面内存，退出或刷新后需重新登录，不保存到 URL、cookie 或浏览器持久存储。

所有管理请求使用 `Authorization: Bearer $BOTS_ADMIN_TOKEN`，路径前缀 `/api/tenants/{tenant}/bots/{bot}`。管理员 token 只绑定本进程的 tenant。

| 方法/后缀 | 请求与行为 |
|---|---|
| `GET` 空后缀 | 当前 Bot、revision、runtime agent、配置引用；不含凭据值 |
| `PUT /enabled`、`PUT /account-enabled` | `{"enabled":false}`；阻断新 claim，已在途结果继续落账 |
| `PUT /config` | `{"expected_revision":1,"config":{完整配置}}`；远端不可变 agent 确认后本地 CAS 激活；已有 thread 保持旧 revision |
| `GET /knowledge`、`/tasks`、`/deliveries`、`/audit` | 返回同名数组包装；支持可选 `scope_id`、`limit=1..100` |
| `GET /tasks/{id}` | 查询本 tenant/Bot/scope 的任务 |
| `POST /knowledge/{id}/deactivate` | `{"expected_revision":1}`；停用内化知识，保留审计 |

`GET /healthz` 仅表示进程存活。工具/timer 回调使用独立服务认证及匹配的 `Idempotency-Key`；模型不能指定身份、频道或回调 URL。

## 4. 分层验证

```sh
GOTOOLCHAIN=go1.26.0 make check
BOTS_TEST_DATABASE_URL='postgres://chronotope:chronotope_dev@127.0.0.1:5432/bots_test?sslmode=disable' GOTOOLCHAIN=go1.26.0 go test -race ./...
python3 test/e2e/mvp.py --mode fake
python3 test/e2e/mvp.py --mode real --model claude-sonnet-4-6
```

`bots_test` 是开发 PG 服务上的独立测试库，须先建立。未配置 `BOTS_TEST_DATABASE_URL` 时 PG tests 明确 skip；CI 提供 PostgreSQL 16，因此运行实际事务测试。测试按随机 tenant 清理，不清空其它测试/开发记录。

E2E 使用真实 Bots 可执行文件、PG、Chronotope API/worker/harness 和 Restate Sleep。只有模型（fake 模式）及渠道 provider 是测试替身；真实模式使用实际模型但仍发往 sink。fake 模式还先拦截 timer 提交，实际 runtime 返回 404 时 SIGKILL Bots，再放行并验证原任务/outbox 修复；该代理只观察技术请求，不实现业务状态。之后在 timer 等待中再次 SIGKILL Bots、重启 worker，暂停期间接纳 fire，恢复后验证确定性发送，再用新 thread recall。脚本不调用真实 Slack API、不删除数据卷。

脚本输出 `/tmp/bots-mvp-*` 下的日志、fixture ledger 和 JSON 报告；捕获的运行时凭据只放在进程环境，报告不保存 key。结束时恢复 api/worker/harness 原配置。证据分别标注 fake、真实模型+sink、真实 Slack，不能混用。开发重建允许清数据，但不算故障恢复证据。

需要手动浏览器 QA 时，设置测试专用 `BOTS_CONSOLE_TEST_TOKEN` 并添加 `--console`。此模式只允许 fake：主路径通过后保留隔离服务与 `/admin`，按回车结束并恢复原栈。它不会修改真实 Bot 的配置，也不是 SOP 改进评测器；一次真实改进的来源、独立对照、人工决议及回退要求见 [SOP 改进验收](SOP改进验收.md)。

Docker 构建器已固定 digest，使用 Go 1.26.9，最终镜像为非 root 的静态 scratch 镜像并包含 HTTPS CA。正常执行 `docker build -t bingdi-bots:mvp .`；若构建网络需要其它 Go 模块代理，可显式传 `--build-arg GOPROXY=https://goproxy.cn,direct`。seed 通过只读文件挂载、凭据通过部署环境注入；构建和容器只读 smoke 证据见[补充验收](evidence/MVP-管理页与崩溃恢复-2026-10-19.md)，不把容器启动等同于完整运行时或真实渠道通过。

## 5. 恢复与未知发送

- Task 与 timer outbox 同事务提交；提交后进程退出，重启使用原 timer ID/revision 修复。到点只由 Chronotope fire 产生 delivery，不扫描到期任务直接发送。
- 工具 operation receipt 保存原结果；成功响应丢失时重放返回原 ID/revision，不再次修改对象。消息重投和单输入提醒槽各自去重。
- provider 确认回执、Task 完成和审计同事务提交。暂时的本地落账失败可重试同一 receipt，绝不再次调用 provider。
- 发送中断或崩溃而未确认结果时记 `unknown`。重启不自动重发、不完成任务；管理员核对原渠道后处理。MVP 不提供自动对账或“任意故障 exactly-once”。
- Bot 暂停或账号禁用阻断新的工具/run/send claim；在途返回仍记账。恢复后可发尚未领取的提醒，超过一分钟标注迟到；unknown 保持待核对。
