# 部署与受控试用

本文是 G0/G1/G2 通过后的上线准备清单。它不改变 MVP 产品合同；未在本机验证的 systemd/compose 模板会明确标注，不能当作已通过的生产部署证据。当前完成度和剩余阻塞项见[P0 上线准备证据](evidence/P0-上线准备-2026-10-20.md)。

## 1. 就绪与存活

| 端点/命令 | 语义 |
|---|---|
| `GET /healthz` | 仅表示进程存活；不检查 PG、租约或 Slack。 |
| `GET /readyz` | 仅当 PG 可查、dispatcher 租约有效、引擎最近 60 秒内完成过 Step，且 Socket Mode（如启用）当前已连接时返回 200；否则返回 503，且不返回依赖错误细节。 |
| `bots readyz` | 用同一二进制探测 `BOTS_PROBE_URL`（默认 `http://127.0.0.1:8090/readyz`），成功退出 0。供 scratch 镜像 HEALTHCHECK 和无 curl 的服务管理器使用。 |

Dockerfile 已包含 `HEALTHCHECK CMD ["/bots","readyz"]`。systemd 或外部监控应轮询 `/readyz`，`/healthz` 只用于判断进程是否还存在。

### 最小可观测性

`GET /metrics` 暴露 Prometheus 文本（无鉴权，仅 loopback/隧道内）：

- `bots_up`、`bots_ready`；
- `bots_inbox_total{state=...}`；
- `bots_tasks_total{status=...}`；
- `bots_deliveries_total{state=...}`，尤其 `unknown`/`rejected`；
- `bots_knowledge_active`。

`scripts/trial-health.sh` 是单次巡检：默认访问 `http://127.0.0.1:8090`，ready 非 1 退出 1，任一 unknown 退出 2；rejected 只报告。可配 cron：

```sh
*/5 * * * * BOTS_URL=http://127.0.0.1:8090 /opt/bingdi-bots/scripts/trial-health.sh >> /var/log/bingdi-trial-health.log 2>&1
```

指标未包含文本、token 或 Slack ID；告警阈值、daily owner 和通知渠道仍需在试用启动前确认。

## 2. 单实例与网络

- 一个 tenant 只能有一个活跃 Bots dispatcher；PG session advisory lock 会拒绝第二实例。不要用多个副本做“高可用”。
- 管理员 API `/api/*`、内部工具 `/internal/tools` 和 timer `/internal/timer-fires` 都在 8090 上。只绑定私网/VPN 或 SSH 隧道；不要把 8090 暴露到公网。
- Socket Mode 只建立出站连接，不需要公网 Request URL；webhook 模式才需要外部 HTTPS。生产试用优先 Socket Mode。
- Chronotope 继续拥有 PG/Restate；不要复制第二套 PG、Restate 或模型服务。
- 若 Bots 运行在宿主机、Chronotope 在 Docker：bridge/timer 回调使用 `http://host.docker.internal:8090`（Linux Docker 需要 `host.docker.internal:host-gateway`）。
- 若 Bots 也在同一 Docker 网络：bridge/timer 回调改为 `http://bots:8090`，并让 api/worker/harness 加入同一网络。`deploy/compose.bots.yml` 是模板。

**2026-10-20 Docker trial**：`bingdi-bots:p0`（当前代码）以只读 rootfs、65532、`no-new-privileges`、`127.0.0.1:8090` 启动，Docker healthcheck `healthy`、`/readyz` 200、Socket Mode connected；真实 Slack recall 验证 Chronotope bridge → 宿主 8090 → 容器的 tool 回调与容器发送（run `r_70081bcc…`，ts `1792484302.646889`）。随后同一镜像以 `bots-trial` 常驻（`--restart unless-stopped`），绑定新租户 `bots-trial-20261020` 和新频道；旧 bot/旧频道数据保留为证据。seed/env 放在 `~/.config/bots/trial`（env 0600），避免 `/tmp` 重启丢失；容器重建后仍 healthy。systemd 仍是可选项，未在目标 Linux 执行。

## 3. systemd 部署（可选；当前 trial 用 Docker）

`deploy/bots.service` 是模板：

```sh
sudo install -d -m 0755 /opt/bingdi-bots /etc/bingdi
sudo install -m 0755 bin/bots /opt/bingdi-bots/bots
sudo install -m 0640 -o root -g bingdi configs/bot.yaml /etc/bingdi/bot.yaml
sudo install -m 0600 -o root -g root /dev/null /etc/bingdi/bots.env
sudo install -m 0644 deploy/bots.service /etc/systemd/system/bots.service
sudo systemctl daemon-reload
sudo systemctl enable --now bots
systemctl status bots
curl -fsS http://127.0.0.1:8090/readyz
```

`/etc/bingdi/bots.env` 只放环境变量，文件权限 0600；不要放进仓库。至少需要：

```sh
BOTS_HTTP_ADDR=0.0.0.0:8090
BOTS_DATABASE_URL=postgres://...
BOTS_SEED_PATH=/etc/bingdi/bot.yaml
BOTS_CHRONOTOPE_URL=http://127.0.0.1:8080
BOTS_CHRONOTOPE_TOKEN=...
BOTS_ADMIN_TOKEN=...
APPLICATION_SERVICE_TOKEN=...
SLACK_BOT_TOKEN=...
SLACK_APP_TOKEN=...
BOTS_PROBE_URL=http://127.0.0.1:8090/readyz
```

服务不自动读取 `.env`；由 systemd `EnvironmentFile` 注入。凭据引用和真实值分开管理，轮换时不需要改 seed。

## 5. 备份与恢复演练

`scripts/backup-bots.sh` 只备份 Bots 自有 `bots` schema；Chronotope 的 run/timer/Restate 状态由另一仓库负责。全栈恢复需要两边协调备份，不能把本脚本当作完整 RTO。

要求 `pg_dump`/`pg_restore` 与 PostgreSQL 服务器主版本一致；脚本会检查并拒绝不匹配的客户端。开发栈的 PG16 可用容器内工具：

```sh
docker exec chronotope-postgres-1 pg_dump -U chronotope -d chronotope \
  --schema=bots --format=custom --no-owner --no-privileges -f /tmp/bots.dump
docker cp chronotope-postgres-1:/tmp/bots.dump ./bots.dump
```

恢复演练必须使用专用数据库（名称以 `bots_restore_` 开头），不能覆盖源库：

```sh
docker exec chronotope-postgres-1 createdb -U chronotope bots_restore_YYYYMMDD
docker cp ./bots.dump chronotope-postgres-1:/tmp/bots.dump
docker exec chronotope-postgres-1 pg_restore -U chronotope -d bots_restore_YYYYMMDD \
  --no-owner --no-privileges /tmp/bots.dump
```

注意：Bots-only dump 恢复时不要再传 `pg_restore --schema=bots`；该过滤会排除 dump 中的 `CREATE SCHEMA bots`，导致恢复后在空 schema 上失败。脚本已处理。验证 `bots.bots` 与 `audit_events` 行数与源库一致后，再删除演练库。

### 全栈备份与 RTO 边界

Bots schema 与 Chronotope 共用同一个 PostgreSQL；Chronotope 已有独立 DR 演练，Bots 不复制一套：

- `../chronotope/test/dr/pitr.sh`（D1）：隔离 PG 容器的 WAL 归档/PITR 演练，覆盖同库的 `bots` schema；要求 WAL 归档开启并记录目标时刻。
- `../chronotope/test/dr/restate-backup.sh`（D3）：Restate 卷快照 → 清空 → 回填 → 挂起审批恢复；会清空/重启 Restate，必须维护窗口，不能对生产栈随意执行。
- `../chronotope/test/dr/rustfs-restore.sh`（D2）：对象存储归档回放。

D1 PITR 已在隔离容器完成 6/6 通过；D3 Restate 卷快照/破坏/恢复/awakeable 5/5 通过。D2 的失败定位为 Chronotope DR 测试脚本过期（未等 run 终态、缺幂等头、SSE 计数、错误 S3 凭据），Chronotope `c7b5e26` 修复后 4/4 通过（replay=base=3）。

**同窗口全栈恢复**：停 trial 和全部服务，卷快照/清空/回填 PG、Restate、RustFS，再启动；服务/trial ready RTO **18.3s**，RPO **0**（计数前后一致），RustFS 对象恢复可读，pending Restate timer 在恢复后 due+3.3s 投递 confirmed。该结果证明本地开发栈的干净停机/卷恢复，不代表生产 HA/连续 PITR。

## 6. unknown / rejected 处置

管理页和 `GET /api/tenants/{tenant}/bots/{bot}/deliveries` 会显示 `unknown`、`rejected`、`retryable`。`unknown` 表示外部效果未知，重启不会重发。

1. 立即暂停 Bot：`PUT .../enabled` 传 `{"enabled":false}`，阻断新的发送/工具 claim。
2. 到原 Slack thread 人工核对文本、时间和目标；保留 thread ts、delivery/task/audit ID。
3. 用管理 API 记录核对结果，**不要**直接改数据库、不要用新 delivery 盲重发：
   ```sh
   # 已在 Slack thread 找到消息时
   curl -X POST "$BOTS_URL/api/tenants/$TENANT/bots/$BOT/deliveries/$DELIVERY/resolve" \
     -H "Authorization: Bearer $BOTS_ADMIN_TOKEN" -H 'Content-Type: application/json' \
     -d '{"state":"confirmed","provider_message_id":"1234567890.123456","note":"checked in Slack thread"}'
   # 确认没有发出时
   curl -X POST "$BOTS_URL/api/tenants/$TENANT/bots/$BOT/deliveries/$DELIVERY/resolve" \
     -H "Authorization: Bearer $BOTS_ADMIN_TOKEN" -H 'Content-Type: application/json' \
     -d '{"state":"rejected","note":"not present in Slack thread; account/channel checked"}'
   ```
   只允许 `unknown`；confirmed 必须带真实 provider message ID，rejected 必须带理由；对应 task 会转为 completed/canceled，并写 `delivery_resolved` 审计。不会调用 provider，也不会重发。
4. `rejected` 检查账号/频道权限和 Slack error；`retryable` 等待 `Retry-After`，不要手工提前重试。
5. 每日检查 `unknown/rejected`；任何 unknown 都要有负责人和结论。

## 8. 试用治理 runbook

单操作者、数据范围、指标阈值、每日巡检、回滚和退出条件见[试用治理 v0.1](试用治理-v0.1.md)。该 runbook 当前待 owner 签核；签核前保持默认最小范围。

### 权限撤回演练（真实频道，维护窗口）

1. 让成员创建一个 2–3 分钟后到期的提醒。
2. 到点前把 Bot 移出测试频道（或撤回频道权限）。
3. 预期：到点发送被 Slack 拒绝，delivery 记录 `rejected`/`blocked`，不盲重发、不重新调度；任务不被标为 completed。
4. 重新邀请 Bot；对 `unknown` 用管理 API resolve，对已明确 rejected 的记录保留原因；不要用新 delivery 重发。
5. 记录 thread ts、delivery/task ID、Slack error 和操作人。

**2026-10-20 已执行真实演练**：移除 Bot 后到点发送返回 `channel_not_found`，delivery 为 `rejected`、task 为 `blocked`、attempts 1，12 秒后无重试；Bot 已重新邀请，`/readyz` 200。blocked task 和演练知识待试用前清理。
